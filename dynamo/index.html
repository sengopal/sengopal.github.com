Dynamo is NVIDIA’s open-source, datacenter-scale inference stack. It runs above engines such as vLLM, SGLang and TensorRT-LLM, and turns many GPUs across many nodes into one serving system. The work touches Rust services, Python engine integrations, GPU data movement, distributed systems and Kubernetes, often in the same week. This page describes the skills I see in engineers who do well on the project. Nobody arrives with all of them. Most people come in strong in two or three areas and pick up the rest on the job.

Systems fundamentals

Everything else on this page builds on a strong grasp of computer architecture and operating systems. You should know how caches, memory hierarchies, NUMA, PCIe and interrupts shape performance. You should also know how the kernel schedules threads, manages virtual memory and moves data through the network stack. Much of Dynamo’s work happens where hardware and software meet. Examples are a pinned buffer that a NIC can reach directly, a thread that wakes on the wrong NUMA node, or a copy that crosses PCIe when it could stay on NVLink. Engineers who understand these interactions can explain a performance result instead of only reporting it, and that is what leads to the right optimization.

Rust and async systems programming

The core of Dynamo is written in Rust. The HTTP frontend, the router, request handling and the runtime that connects workers are async Rust services built on Tokio. You should be comfortable with ownership and lifetimes across async boundaries, with cancellation, and with streams that carry tokens back to a client one at a time. Much of the hard work is in the paths that go wrong: a client disconnects mid-stream, a worker dies during decode, or a node drains for an upgrade. Engineers who do well here think about those cases first and write tests for them.

Python and the engine layer

Each backend worker is a Python process that wraps an inference engine, and it talks to the Rust runtime through PyO3 bindings. That boundary is where many subtle bugs live, such as the GIL, event loops on both sides, and object lifetimes across languages. You need to read the vLLM, SGLang and TensorRT-LLM code well enough to know what the engine does with a request. That includes the scheduler, the KV cache manager, and how the engine reports metrics and errors.

How LLM inference works

Most design decisions in Dynamo follow from how an LLM serves a request. You should know the difference between prefill and decode, and why one is compute-bound and the other memory-bound. You should understand how the KV cache grows and gets evicted, and why prefix reuse matters for routing. Continuous batching, chunked prefill, speculative decoding, quantization, and tensor, pipeline, data and expert parallelism all show up in day-to-day work. Disaggregated serving, where prefill and decode run on separate GPU pools, is one of Dynamo’s central features. To reason about it you need to know what it costs to move a KV cache between those pools.

GPU communication and data movement

Moving bytes between GPUs, hosts and storage is often the bottleneck. Dynamo uses NIXL to transfer KV cache blocks over NVLink, InfiniBand or RoCE, and to offload them to host memory and storage. You will get more done if you understand RDMA, GPUDirect, UCX, the NVLink and network topology of the machines you run on, and what NCCL collectives do during tensor and expert parallelism. Some CUDA knowledge helps too: streams, events, pinned memory and asynchronous copies. You rarely need to write kernels, but you do need to read a profile and tell whether the GPU is computing, waiting on memory or waiting on the network.

Distributed systems

A Dynamo deployment is a distributed system with a frontend, routers, prefill workers, decode workers and a planner that scales them. You should be comfortable with service discovery, leases, health checks and backpressure. You should also know the failure modes that come with them: split views of membership, retries that double the load, and slow nodes that look healthy. The KV-aware router picks a worker by estimating how much of a request’s prefix is already cached. The planner adds and removes workers to meet latency targets. Both depend on accurate, timely state from across the cluster. Request migration, cancellation and graceful shutdown are what keep a long generation alive when a worker goes away.

Kubernetes and deployment

Most production users run Dynamo on Kubernetes. The Dynamo operator manages a whole inference graph as one custom resource. You should know how operators and custom resources work, how pods get scheduled onto GPU nodes, and how multi-node workers are placed together. Helm, container images, and the NVIDIA GPU and network operators are part of the daily routine. Many bugs reported by users turn out to be deployment problems, so being able to read a cluster’s state quickly saves a lot of time.

Performance engineering

Performance is the reason Dynamo exists, so every change needs numbers behind it. You should be able to design a benchmark that matches a real workload, with realistic input and output lengths, concurrency and prefix reuse. You should report time to first token, inter-token latency and throughput at the percentiles that matter. Nsight Systems, perf, flame graphs and tokio-console are the usual tools for finding where time goes. Prometheus metrics and tracing tell you what happened in a deployment after the fact. The best results come from engineers who form a hypothesis, measure, and change one thing at a time.

Working in the open

Dynamo is developed on GitHub with contributors inside and outside NVIDIA. Clear pull requests, design proposals that others can review, and patient answers to user issues are part of the job. Many of the most useful changes start in a GitHub issue from someone running Dynamo in production. You will also work upstream with the vLLM, SGLang and TensorRT-LLM communities, so it helps to know how those projects review and merge code.

Ways to stand out

Some experience is not required but makes a candidate stand out.

Experience with parallel programming models such as MPI and SHMEM helps a lot. So does hands-on work with at least one communication runtime, such as MPI, NCCL, NVSHMEM, OpenSHMEM, UCX or UCC. People who have written parallel code with CUDA, MPI, OpenMP, OpenACC or pthreads already think about synchronization, data placement and overlap of compute with communication. Those same ideas drive KV cache transfer and multi-node serving.

A background in RDMA and high-performance networking is also valuable. That includes InfiniBand, RoCE, Ethernet and EFA, along with network architecture and topologies such as fat trees, rails and NVLink domains. Add a working knowledge of HPC and of ML and deep learning fundamentals, and you can reason about a deployment from the model down to the wire.

Experience implementing or directly using GPU programming APIs such as CUDA, OpenCL, OpenGL or Vulkan shows that you understand how work and memory get onto a GPU. That understanding helps when you read a profile or debug a transfer.

Finally, the project moves fast. People who can balance several projects with competing priorities, and say clearly what they will and won’t get to, are the ones others rely on.
