Neuron - Handling NaNs

  • Compiler options in neuronx-cc
  • Finding NaN values in a BF16 dump
  • Locating the first NaN
  • References

A NaN (Not a Number) in a model’s output usually starts as an infinity or an invalid operation in one intermediate tensor, then spreads through every later operation that reads it. Under IEEE 754 rules, inf - inf, 0 * inf and inf / inf all produce NaN, and any arithmetic with a NaN input produces NaN.

In LLM inference, the common sources are:

  • Overflow to infinity. A value larger than the largest finite number of the data type becomes infinity. The largest finite FP16 value is 65,504. BF16 has the same exponent range as FP32, and its largest finite value is about 3.39 × 10³⁸, so overflow is rarer in BF16, but it can still happen in a sum of many large values or in exp of a large input.
  • Fully masked rows in attention. An attention mask sets blocked positions to negative infinity before the softmax. If every position in a row is blocked, the softmax subtracts the row maximum, which is also negative infinity, and computes exp(-inf - (-inf)). The result is NaN for the whole row. A padded row in a batch is a typical case. Masks that use a large finite negative value instead of infinity avoid this.
  • Precision loss in reductions. A long sum or a variance computed in BF16 loses low-order bits. The result is wrong rather than NaN. A variance computed as E[x²] − E[x]² can then come out negative or zero and produce NaN or infinity in a later square root or division.

Compiler options in neuronx-cc

The Neuron compiler, neuronx-cc, has two options that address these cases.

--enable-saturate-infinity was added in compiler version 2.7.0.40 in June 2023. It converts positive and negative infinity to the largest and smallest finite values before operations that would turn an infinite input into NaN. As of April 2024, the compiler reference limits it to the matrix-multiply transpose computations that the compiler introduces. The conversion has a runtime cost.

--enable-mixed-precision-accumulation was added in compiler version 2.13.66.0 in April 2024. It performs the intermediate steps of reduction operators, such as dot products, softmax and layer normalization, in FP32, and casts the result back to the model’s data type, for example BF16. This keeps the extra precision of FP32 inside the reduction while the tensors stay in BF16.

Both options apply at compile time. With torch-neuronx, the NEURON_CC_FLAGS environment variable passes them to the compiler:

export NEURON_CC_FLAGS="--enable-saturate-infinity --enable-mixed-precision-accumulation"

Finding NaN values in a BF16 dump

An intermediate tensor saved from a device run is often a buffer of raw 16-bit values. NumPy has no bfloat16 data type, so np.isnan cannot read these values directly. A BF16 value is the upper 16 bits of the FP32 value with the same sign and exponent. Shifting the bits left by 16 gives a valid FP32 bit pattern:

BF16 bits Value
0x3f80 1.0
0xbf80 -1.0
0x4000 2.0
0x7f80 +inf
0xff80 -inf
0x7fc0 NaN

The conversion in NumPy works on the whole buffer at once:

import numpy as np

raw = np.array([0x3f80, 0xbf80, 0x4000, 0x7f80, 0xff80, 0x7fc0], dtype=np.uint16)
f32 = (raw.astype(np.uint32) << 16).view(np.float32)

print(f32)            # [  1.  -1.   2.  inf -inf  nan]
print(np.isnan(f32))  # [False False False False False  True]
print(np.isinf(f32))  # [False False False  True  True False]

PyTorch supports bfloat16 directly. Reinterpreting the same bits as a BF16 tensor lets torch.isnan and torch.isinf run on them without a copy to FP32:

import torch

t = torch.from_numpy(raw.view(np.int16)).view(torch.bfloat16)
torch.isnan(t)  # tensor([False, False, False, False, False,  True])

Locating the first NaN

A NaN in the final logits says little about where it started. The first check is whether the NaN reproduces on CPU with the same inputs and BF16 weights. If it does, the model itself produces it, and forward hooks in eager mode record the first module whose output contains NaN or infinity:

def find_first_nonfinite(model, inputs):
    found = []

    def hook(module, args, output):
        if not found and isinstance(output, torch.Tensor) and not torch.isfinite(output).all():
            found.append(module)

    handles = [m.register_forward_hook(hook) for m in model.modules()]
    try:
        model(*inputs)
    finally:
        for h in handles:
            h.remove()
    return found[0] if found else None

A module’s hook runs when its forward pass returns, so a layer’s hook fires before the hook of the container that holds it. The first module recorded is the innermost, earliest module with a non-finite output.

If the NaN appears only on the device, the compiled graph differs from the eager model, for example in casts the compiler inserted or in the precision of a reduction. Recompiling with the two options above is a quick test of those two causes.
