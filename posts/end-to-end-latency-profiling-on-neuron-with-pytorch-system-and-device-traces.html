End-to-End Latency Profiling on Neuron with PyTorch, System and Device Traces

Inference latency on Neuron can be measured at three levels. The PyTorch profiler records what the host CPU does, including framework code, input preparation, and the calls that dispatch work to the device. The Neuron runtime system trace records runtime and device events across the whole run, such as each model execution on a NeuronCore and each collective operation. neuron-profile records what happens inside the device during a single execution of a compiled model (NEFF). An investigation usually moves through the three levels in that order, from the broadest view to the narrowest.

Choosing a profiler

The PyTorch profiler captures:

  • CPU activity, including PyTorch operators and framework overhead
  • Input preparation on the host
  • The duration of each call to the Neuron device, including the wait for the result
  • The split between context encoding, which processes the prompt, and token generation, which produces one token per step

The system trace captures:

  • The start and end of every NEFF execution on every NeuronCore
  • Collective operations and the barriers between them
  • Model switches, tensor reads and writes, and numerical errors
  • Idle gaps between executions and the timing between NeuronCores

The device profile captures:

  • Activity inside one NEFF execution
  • Per-engine activity, DMA transfers, collectives and semaphores

When time to first token or per-token latency is higher than expected, the PyTorch profile shows whether the time goes to the host or the device. The system trace shows how device executions are spaced across the run and across NeuronCores, which exposes gaps, stalls and long tails that a single execution does not show. The device profile then explains a slow execution operator by operator.

Capturing a PyTorch profile

A minimal capture around a transformers-neuronx generation call:

from torch.profiler import profile, ProfilerActivity

# Warm-up run, excluded from the profile.
model.sample(input_ids=input_ids, sequence_length=input_length + output_size, top_k=1)

with profile(activities=[ProfilerActivity.CPU]) as prof:
    model.sample(
        input_ids=input_ids,
        sequence_length=input_length + output_size,
        top_k=1,
    )

prof.export_chrome_trace("torch_profile.json")

ProfilerActivity.CPU records the host-side operators. The warm-up call keeps one-time costs, such as loading the model onto the device and filling caches, out of the measurement. The exported file uses the Chrome trace JSON format.

Each call into the Neuron runtime appears in the trace as a host-side operator. In the transformers-neuronx traces used here, the call is named neuron::_parallel_executor_run, and its duration covers dispatching the work and waiting for the device to finish. Operator names can differ between SDK versions, so the names in the queries below should be checked against the trace first.

Viewing the PyTorch trace

Perfetto opens Chrome trace files directly in the browser and handles large traces better than the older chrome://tracing viewer. Each operator appears as a slice on a timeline. Hovering over a slice shows its duration, and selecting a range of slices shows aggregate statistics.

Querying the PyTorch trace with SQL

Perfetto loads the trace into a database and accepts SQL in its query tab. The slice table holds one row per slice, with the start time ts and duration dur in nanoseconds.

Duration of each device call. Dividing by 1e6 converts nanoseconds to milliseconds:

SELECT ts, dur / 1e6 AS duration_ms
FROM slice
WHERE name = 'neuron::_parallel_executor_run'
ORDER BY ts;

Context encoding latency. The first device call of a generation processes the prompt, so its duration approximates the context encoding latency:

SELECT dur / 1e6 AS context_encoding_ms
FROM slice
WHERE name = 'neuron::_parallel_executor_run'
ORDER BY ts
LIMIT 1;

Per-token latency. The time between the starts of two consecutive device calls is the latency of one generated token as the application sees it, including any host-side gap between calls. LAG() returns the previous row’s timestamp, and the first call has no predecessor:

SELECT (ts - LAG(ts) OVER (ORDER BY ts)) / 1e6 AS token_latency_ms
FROM slice
WHERE name = 'neuron::_parallel_executor_run'
ORDER BY ts;

Average token generation latency. Averaging the gaps and dropping the first row gives the mean per-token latency:

SELECT AVG(token_latency_ms) AS avg_token_latency_ms
FROM (
    SELECT (ts - LAG(ts) OVER (ORDER BY ts)) / 1e6 AS token_latency_ms
    FROM slice
    WHERE name = 'neuron::_parallel_executor_run'
)
WHERE token_latency_ms IS NOT NULL;

These queries assume one slice per device call. If several threads each record the call, the queries should filter on a single thread first. Percentiles are easiest to compute by exporting the query result and processing it with NumPy.

Capturing a system trace

The PyTorch profile sees each device call as a single host-side slice. The Neuron runtime system trace records what the runtime and the NeuronCores do during those calls, continuously and for every core, while the application runs normally. It does not show the instructions inside an execution. An event says that a NEFF ran on a NeuronCore from one time to another, not which engine instruction ran at a given moment.

Capturing with environment variables

The runtime captures a system trace for an unmodified application when NEURON_RT_INSPECT_ENABLE is set (system profiles overview, capture guide):

export NEURON_RT_INSPECT_ENABLE=1
export NEURON_RT_INSPECT_OUTPUT_DIR=./inspect-output
export NEURON_RT_INSPECT_EVENT_FILTER_NC=0-3
export NEURON_RT_INSPECT_EVENT_FILTER_TYPE=hardware
python run_inference.py

The other NEURON_RT_INSPECT_* variables have no effect unless NEURON_RT_INSPECT_ENABLE=1 is set. The two filter variables restrict capture to NeuronCores 0 to 3 and to hardware events. NEURON_RT_INSPECT_DEVICE_PROFILE=1 also captures device profiles of the executed NEFFs. The trace covers the whole lifetime of the process, and Neuron Explorer opens the output directory:

neuron-explorer view -d ./inspect-output

Capturing with the runtime API

For control over when capture starts and stops, the runtime exposes the trace through a C API in nrt_sys_trace.h (API reference). The runtime stores events in per-NeuronCore ring buffers, so the trace can run for a long time with bounded memory. Events are returned as a JSON string and can be fetched only once. The ring buffers are freed when tracing stops, so the events must be fetched before nrt_sys_trace_stop():

#include <stdio.h>
#include <nrt/nrt_sys_trace.h>

nrt_sys_trace_config_t *config = NULL;
nrt_sys_trace_config_allocate(&config);
nrt_sys_trace_config_set_defaults(config);
nrt_sys_trace_start(config);

/* Run the workload: an inference batch or a training step. */

char *events = NULL;
size_t size = 0;
nrt_sys_trace_fetch_events(&events, &size, NULL);
fwrite(events, 1, size, output_file);
nrt_sys_trace_buffer_free(events);

nrt_sys_trace_stop();
nrt_sys_trace_config_free(config);

The configuration controls how much the trace captures:

  • nrt_sys_trace_config_set_max_events_per_nc() sets the capacity of the ring buffers.
  • nrt_sys_trace_config_set_capture_enabled_for_nc() turns capture on or off for a NeuronCore. The runtime allocates no ring buffer for a disabled core.
  • nrt_sys_trace_config_set_capture_enabled_for_event_type() turns capture on or off for an event type.

An unfiltered trace of a long run produces a very large number of events. Restricting capture to the event types and NeuronCores under investigation keeps the trace small enough to analyze.

Event types

nrt_sys_trace_get_event_types() returns the full list of event types for the installed runtime. The hardware events include:

  • nc_exec_running, the execution of a NEFF on a NeuronCore
  • cc_running and cc_exec_barrier, collective operations and their barriers
  • nrt_model_switch, a switch between loaded models
  • numerical_err, a numerical error such as a NaN or an infinity
  • timestamp_sync_point, a timestamp synchronization event
  • hw_notify, a hardware notification

The software events cover runtime activity on the host, such as model_load, nrt_execute, tensor_read and tensor_write.

Analyzing the system trace

Neuron Explorer shows the events on a timeline. Events fetched through the API are plain JSON, which a short Python script can process. Typical analyses include:

  • The distribution of NEFF execution durations from nc_exec_running events
  • The intervals between the starts of consecutive executions, which include any host-side gap
  • The time spent in cc_exec_barrier, which shows NeuronCores waiting on each other in a collective
  • The timing of numerical_err events relative to the executions around them

Capturing a device profile

The PyTorch profile and the system trace show which NEFF execution is slow. neuron-profile shows what happens inside that execution:

neuron-profile capture -n file.neff -s profile.ntff

The capture runs the NEFF on the device and writes the trace to an NTFF file. Models that run across several NeuronCores need the multi-worker options described in the Neuron Profile user guide.

Viewing the device profile

The web viewer stores the processed trace in InfluxDB 2.x, which must be installed and initialized once on the instance. The user guide lists the installation steps. After that, the following command processes the profile and prints a local URL, usually on port 3001:

neuron-profile view -n file.neff -s profile.ntff

When the profile runs on a remote instance, SSH port forwarding makes the viewer reachable from a laptop:

ssh my-instance -L 3001:localhost:3001 -L 8086:localhost:8086

The viewer is then available at http://localhost:3001.

Newer Neuron SDK releases replace neuron-profile with neuron-explorer, which takes the same capture arguments (neuron-explorer capture -n file.neff -s profile.ntff) and needs no InfluxDB installation (migration guide).

A worked example

Consider a generation of 100 tokens that takes 800 ms when the expected latency is 400 ms.

  1. PyTorch profile. Capture one generation after a warm-up run and open it in Perfetto.
  2. Context encoding. The context encoding query returns 150 ms. Context encoding accounts for less than a fifth of the total.
  3. Token generation. The average token latency query returns 6.5 ms. Over 100 tokens, token generation accounts for 650 ms, so it is the phase to investigate.
  4. Host or device. The durations of the token generation calls are close to the gaps between them, so little time is spent on the host between tokens. The time goes to the device.
  5. System trace. The nc_exec_running events for the token generation NEFF show the same duration on every NeuronCore, and the cc_exec_barrier events show each core waiting a large share of every step. The time goes to collectives, not to computation on one slow core.
  6. Device profile. A neuron-profile capture of the token generation NEFF shows which engines wait on DMA or collectives, which narrows the problem to specific operators.

Practices

Move from broad to narrow. The PyTorch profile locates the slow phase, the system trace shows how executions behave across the run and across NeuronCores, and the device profile shows which operators in an execution take the time.

Reuse the queries. Running the same SQL queries and scripts on every profile gives a record of normal values for a model, and a regression shows up as a departure from those values.

Exclude warm-up. The first execution includes one-time costs such as loading the model and filling caches. A warm-up run before the profiled run keeps these costs out of the measurement.

Filter the system trace. Capturing only the relevant event types and NeuronCores keeps long traces small enough to analyze.

Script long traces. For long captures, scripted analysis with the Perfetto trace processor or a Python script over the system trace is faster than scrolling through a UI.
